# 单据自动汇总核算服务 - 可行性与报价评估（内部）

> 内部评估存档，**不要直接发给客户**。对客户的版本见 `proposal-v2.md` 与 `quotation.md`。
> 评估前提：客户选定交付形态为 Windows 桌面 exe（客户不接触命令行），隐私口径为可接受云端 API 调用。

## 一、可行性结论

整体可行，无技术攻关点，全部是成熟工程组合。按模块给出确定性评级：

- **目录扫描与归档结构初始化** - 确定可做。纯文件系统操作。
- **Excel / 供应商对账表读取** - 确定可做，但工作量易被低估。每家供应商的表头、列序、合并单元格、多 sheet 都不同，必须做列名映射配置层，不能硬编码。
- **图片单据 OCR 与字段抽取** - 可做，但**准确率不可承诺 100%**。这是全案唯一的实质风险，见第四节。
- **汇总与 Excel 输出** - 确定可做。openpyxl 多 sheet + 明细/汇总双层 + 溯源列。
- **Windows GUI + exe 打包** - 确定可做，但打包兼容性（体积、杀毒误报、客户机无 Python 环境）是隐性工时黑洞。
- **不修改原始文件** - 确定可做，且应在代码层用只读方式打开强制保证，而非仅靠承诺。

## 二、方案书必须修正的三处缺陷

这三处若按原文交付，会在验收或第二个月使用时爆发。

### 1. 「数据不外传」与「借助 AI 识别」直接矛盾

原文承诺「数据不会外传，保障进货价、成本等经营隐私」，但云端多模态模型必然要上传图片。这是表述性风险，客户一旦追问即信任崩塌。

改为明示口径：原始单据与汇总结果**仅存本地**；识别过程中图片经加密通道传给大模型服务商、用完即弃、不落任何第三方数据库、不参与训练。同时把敏感度最高的项目（房租、水电等固定开支金额）走本地规则解析、不过云。

### 2. 「手动将多份明细表格合并为完整总表」是设计缺陷，不是适配方案

原文第四节把分批合并的负担丢给客户，与「大幅缩减对账耗时」的卖点自相矛盾，也是最容易被客诉的点。

正确做法是**单据级缓存 + 断点续跑**：每张单据识别结果以图片哈希为键落地为本地 JSON，程序自动分批、失败自动重试、中断后从断点继续，最后统一汇总。客户永远只看到一张总表。改动约 1 人天，直接消除方案里最丑的一块。

### 3. 缺少人工复核结果的回写闭环

原文第七节要求客户「对照原始单据人工复核修正」，却没说修正后怎么办。第二个月重新汇总时，客户改过的值会被 AI 重新覆盖，等于白改。

需要修正持久化：客户在总表里改动的字段回写到该单据的缓存 JSON 并标记「已人工确认」，后续汇总跳过重识别、直接采用确认值。这一条是把工具从「一次性玩具」变成「能长期用」的分界线。

## 三、增值卖点（低成本、高感知）

开发成本很低，但客户感知价值远高于「把单据变成表格」，建议加入以提升报价空间：

- **重复单据与漏单检测** - 同供应商同日期同金额告警、单据号断号提示。对账场景里这是最值钱的能力，约 0.5 人天。
- **低置信度自动标黄** - 让模型输出每个字段的置信度，低于阈值的单元格标黄并附原图路径，把「全表复核」压缩成「只核标黄项」。这是应对准确率风险的产品化手段。
- **同比 / 环比对比** - 本月各供应商进货额与上月对比，异常波动标注。约 0.5 人天。
- **营收手工录入一栏** - 原方案声明「不计算净利润」。只需在总表加一个营收输入单元格即可自动出毛利。边界从「支出明细」跃升到「利润测算」，卖点提升明显，成本近乎为零。

## 四、准确率风险与验收标准

CIKM 2026 的 OmniHandwritingOCR 基准（arXiv 2608.18586）结论：13 个主流开闭源系统中最优者（Qwen3-VL-8B）综合分仅 72.16，且多个生成式模型会产生「视觉无依据的合理化纠错」，即把模糊数字**补成看起来合理的值**而不报告不确定。垂直商业引擎（TextIn 宣称手写 97%、中集飞瞳宣称 99%）表现更好，但需额外付费。

对「印刷表格 + 手写金额」的混合单据，现实预期为字段级准确率 85~95%，金额与数量字段最易出错（7/1、3/8 混淆、涂改）。

**合同里必须写死的验收标准**（否则会陷入无限返工）：

- 以客户提供的 50~100 张真实单据为验收集
- 关键字段（日期、供应商、金额）字段级准确率 >= 92%
- 每行明细必须可溯源到原始图片文件名
- 低置信度字段必须标记，不得静默输出
- **明确免责**：字迹潦草、拍摄模糊、涂改、反光的单据不计入准确率统计，但必须被标记为「需人工确认」而非丢弃

最后一条尤其重要：可接受的失败是「我不确定，请你看」，不可接受的失败是「猜一个数写进去」。

## 五、工期估算

单人开发，AI 辅助，单位为人天：

| 工作项 | 人天 |
|---|---|
| 需求确认 + 真实样本收集分析 | 1 |
| 目录扫描与归档结构初始化 | 0.5 |
| 配置管理（Key 加密存储、模型选择、并发参数） | 0.5 |
| OCR 调用层（重试、限流、并发、失败队列） | 1.5 |
| 字段抽取与结构化（提示词迭代 + schema 校验 + 金额日期归一化） | 2 |
| Excel 读取适配层（列名映射、多格式兼容） | 1.5 |
| 汇总与 Excel 输出（多 sheet、溯源、标黄） | 1.5 |
| 单据级缓存 + 断点续跑 + 修正回写 | 1.5 |
| 增值功能（查重、环比、毛利） | 1 |
| GUI 开发（目录选择、月份勾选、进度条、日志） | 2.5 |
| 打包与兼容测试（PyInstaller、杀软误报、干净机验证） | 1.5 |
| 真实样本调优 | 2 |
| 部署培训 + 图文说明书 | 1 |
| 缓冲（约 15%） | 2 |

**合计 20 人天**，区间 18~22 人天。

**日历工期**：全职 4 周；兼职（晚间与周末）6~8 周。中间需等客户提供真实样本，**对外承诺 5~6 周**，留出缓冲。

## 六、报价建议

### 成本底数

- 开发人力 20 人天，独立开发者市价 800~1500 元/人天，**人力成本 1.6~3.0 万**
- AI 调用费：qwen-vl-max 华北2 原价输入 0.229 美元/百万 token、输出 0.573 美元/百万 token（2026-09-03 查证）。单张单据约 1300 输入 token + 300 输出 token，**每张 0.005~0.02 元**；月 300 张约 2~6 元，**年成本不足 100 元，可直接包含在服务费内**
- 售后支持：首年预留 2~3 人天

结论：AI 调用费不是成本项，不要设计按量计费，也不要让客户自己申请 Key——省下的解释成本比这点钱值钱得多。

### 三档定价

- **轻量版 4000~6000 元，工期 3~5 天**。不做 exe，客户电脑装现成 AI 客户端，交付文件夹规范 + 提示词包 + 输出模板 + 培训。**建议先卖这一档做验证**，跑通一个月再升级。
- **标准版 15000~20000 元，工期 5~6 周**。GUI exe 单客户定制，含第二节全部修正、第三节增值功能、上门部署培训、3 个月售后。与 20 人天成本匹配的合理价位。
- **产品化路线（推荐）**。同一套工具卖多个同类客户，单客户一次性 3000~5000 元或年费 1500~2500 元。首次投入 22~25 人天（多 3~5 人天做配置化），之后每单边际成本仅剩部署培训 0.5 人天。卖到第 5 个客户回本，第 10 个开始纯利。

**风险提示**：目标客户是个体商户或小批发商，痛点货币价值约为每月省 2 天人工、年化 5000~8000 元。一次性支付 1.5~2 万的成交概率偏低，需做好被压价预期。产品化是唯一能让 20 人天投入在经济上成立的模式。

### 付款方式

40% 预付 / 40% 验收通过 / 20% 稳定运行一个月后结清。尾款与「客户完整跑通一个月度对账」绑定，既降低客户决策风险，也保护自己不被无限返工拖住。

## 七、需要客户确认才能锁定报价的信息

- 月单据量级（50 张 / 300 张 / 1000 张以上）
- 手写单据占比，能否先提供 20~30 张真实照片做识别测试
- 供应商 Excel 对账表有几种不同格式
- 客户电脑配置与 Windows 版本，是否有杀毒软件管控
- 是否需要多台电脑同时使用

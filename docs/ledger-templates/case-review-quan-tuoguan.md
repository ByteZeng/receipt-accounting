# 案例图研判：全托管场景下的大表修订依据

依据：`projects/receipt-accounting/src/` 五份样本 + 需求方说明「主要做 Temu / 速卖通全托管」。

## 样本分别是什么

| 文件 | 实际内容 | 对应业务 |
|------|----------|----------|
| 供应商手写单.jpg | 印刷送货单 + 手写：货号、品名、按尺码的包数、总包/总件；金额栏常空 | 进货原始凭证 |
| 供应商台账.png | 按客户分块、尺码矩阵（XS~3XL）、小计、单价、金额；同款大码单价更高 | 进货/调货台账（矩阵录入习惯） |
| 初步汇总表.png | 按合作厂+货号汇总：金额、袋子总价、件数、总包数、分码包数、分码单价、袋子规格价 | 进货月汇总（已含包材） |
| 出库退供表.png | 多 sheet：速卖通 / TK自营出库 / 代发 / 速卖通退供 / TEMU退供；代发页含件套、单价/条、袋子费 | 出库 + 退供 + 代发结算 |
| 汇总表2.png | 总账本 tab：总额、支出、支出明细、提货明细、退供、提现、工资表（跨年） | 需求方现有「完整账」骨架 |

## 模式判断（置信度高）

1. **主业是全托管送仓，不是卖家直发终端买家。** 收入主路径是「平台结算 → 提现」，不是「销售出库确认收入」。
2. **退供是一等公民。** 现账本单独有「退供TEMU / 速卖通退供 / 年退供」多页，说明退供频率和金额都值得独立成表。
3. **同时存在 TK 自营与外部代发（如欣巧儿）。** 大表「出库类型」必须能区分：Temu送仓 / 速卖通送仓 / TK自营出库 / 代发出库。
4. **计量单位是内衣行业口径：** 包、件/条、件装数（3/4/5/6件装）并存；只记「数量」一行不够。
5. **价格按尺码段变化。** 同货号 M/L 一个价、2XL-3XL 更高价，商品档案与进货都必须支持「分码单价」。
6. **袋子/包装费几乎每单都跟。** 规格（如 20*30）+ 单价（如 0.145）是进货成本组成部分，不是可有可无的备注。

## 对上一版大表的修正结论

| 上一版设计 | 全托管实测后 |
|------------|--------------|
| 强调亚马逊 FBA / 一件代发销售订单 | 降权；全托管以「送仓 + 提现」为主 |
| 「库存可后补」写成开放题 | 仍要库存，但粒度改为：国内仓 ↔ 已送平台（在途/平台仓）↔ 退供回仓 |
| 出货明细混备货与销售 | 改名为「出库明细」，类型按平台/自营/代发拆 |
| 无退供表 | **必增「退供明细」** |
| 收支里「平台回款」一笔 | **必增或单列「提现明细」**，对齐他们现有账本语言 |
| 员工分包偏仓库计件 | 保留，并兼容「代发厂结算」（欣巧儿类） |
| SKU 一行一色一码 | 保留长表（利于 AI）；指引中承认他们习惯矩阵录入，可先矩阵再展开 |

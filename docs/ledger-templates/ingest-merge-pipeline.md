# 手写单 / 供应商台账 → 大表：识别与合并方案

> 回答：后续单据多了，怎么识别，怎么合进规划好的大表。
> 一期主落点是 **提货明细**；出库/退供/提现用同一套「识别 → 标准化 → 去重合并 → 人工确认」骨架，换抽取模板即可。

---

## 一、总体流程（一张图说清）

```text
日常丢文件
  月份/提货/手写单/*.jpg
  月份/提货/供应商台账/*.xlsx|*.png
           │
           ▼
    ┌──────────────┐
    │ 1. 归类扫描   │  按扩展名+目录+轻量分类，分成「手写单」「台账表」
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ 2. 抽取       │  手写单 → 视觉模型 OCR
    │              │  台账 Excel → 规则+列名映射（截图台账才走 OCR）
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ 3. 标准化展开 │  尺码矩阵 → 一行一码；包×件装=件数；货号对齐商品档案
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ 4. 互补合并   │  手写单常无单价 → 用同日同厂同货号台账补价
    │              │  台账常缺原始单号 → 用手写单号做溯源
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ 5. 去重入库   │  以「内容指纹」判断是否已进大表；只追加新行
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ 6. 人工复核   │  低置信度/冲突行标黄；改完回写「已确认」
    └──────┬───────┘
           ▼
         提货明细（大表）
```

**原则：原始文件只读、永不改名移动；大表只追加或更新「系统写入区」；人改过的行优先于 AI。**

## 二、两类来源分别怎么识别

### A. 手写送货单（照片 / 扫描件）

**输入特征**（见 `src/供应商手写单.jpg`）：印刷送货单 + 蓝笔；货号、品名、分码包数写在规格栏；总包/总件；**金额栏经常空白**。

**抽取目标（JSON，一行一码展开前可先保留矩阵）**：

```json
{
  "source_type": "handwritten_delivery",
  "date": "2026-08-03",
  "doc_no": "26109739",
  "supplier": "兴发厂或收货单位旁注",
  "receiver": "森风棠",
  "lines": [
    {
      "sku": "3031",
      "name": "保暖棉三角",
      "pack_size": 6,
      "sizes": {"XL": 5, "2XL": 12},
      "packs_total": 17,
      "pieces_total": 102,
      "unit_price": null,
      "amount": null,
      "confidence": 0.82
    }
  ],
  "notes": "金额栏空白",
  "source_file": "送货单_0812.jpg"
}
```

**技术要点**：

- 沿用现有 `spike/`：多模态模型 +「不确定就留空」提示词（必须保留，手写金额空白时禁止瞎补价）。
- **必须升级现有通用抽取 schema**：增加 `pack_size`、`sizes{}`、`packs_total`、`pieces_total`；校验 `sum(sizes) == packs_total`、`packs × pack_size == pieces`（不符则标黄，不自动改数）。
- 结果按图片哈希缓存；同一张图不重复计费。

### B. 供应商台账（Excel 优先，截图次之）

**输入特征**（见 `src/供应商台账.png`、`初步汇总表.png`）：尺码横排矩阵、分码单价、袋子规格/单价、按厂或按客户分块。

**抽取策略**：

| 文件类型 | 做法 |
|----------|------|
| `.xlsx` / `.xls` / `.csv` | **不要走 OCR**。用 openpyxl 读单元格；为每个厂维护一份「列名映射配置」 |
| 台账截图 `.png/.jpg` | 当「表格图像」走视觉模型，提示词要求输出与 Excel 相同的中间 JSON |

**中间 JSON 与手写单对齐**（方便后合并）：

```json
{
  "source_type": "supplier_ledger",
  "date": "2026-08-09",
  "supplier": "东棠或合作厂名",
  "lines": [
    {
      "sku": "3031",
      "name": "保暖棉三角",
      "size": "M",
      "packs": 10,
      "pack_size": 6,
      "pieces": 60,
      "unit_price": 3.6,
      "bag_spec": "20*30",
      "bag_unit_price": 0.145,
      "bag_qty": 10,
      "amount": 216.0
    }
  ],
  "source_file": "台账_0809.xlsx"
}
```

矩阵表在读取时就 **展开成一行一码**，不要把 XS~3XL 塞进大表一行。

## 三、标准化：变成「提货明细」行

每条中间记录映射到大表字段：

| 提货明细列 | 来自 |
|------------|------|
| 日期 / 单据号 / 合作厂 | 单据头 |
| 货号 / 品名 / 尺码 | 行项目；货号经商品档案归一（3031# → 3031） |
| 包数 / 件装数 / 件数 | 行项目；缺件装数则查商品档案默认件装 |
| 单价 / 货款金额 | 台账优先；手写单常空 |
| 袋子规格/单价/数量/金额 | 台账或汇总表 |
| 原始凭证 | 源文件名 |
| 备注 | 校验冲突、补价来源说明 |

**商品档案的作用**：统一货号写法、默认件装数、大码默认加价。识别结果里货号不在档案中 → 仍入库，但标「新货号待建档」。

## 四、合并规则（最关键）

手写单和台账经常描述**同一批货**，不能简单两份都追加，否则数量翻倍。

### 1. 行指纹（用于去重）

```text
fingerprint = 日期 + 合作厂 + 货号 + 尺码 + 包数 + 件数 + 来源类型
```

同一指纹已存在且状态为「已确认」→ 跳过。  
同一指纹存在但未确认、新结果置信度更高 → 更新候选，仍标黄待审。

### 2. 互补合并（推荐默认策略）

| 情况 | 处理 |
|------|------|
| 只有手写单 | 入库数量字段；单价/金额空着；备注「待台账补价」 |
| 只有台账 | 入库数量+价格；单据号可空；备注「无手写单溯源」 |
| 两者同日同厂同货号尺码，数量一致 | **合并成一行**：数量以手写单为准（原始凭证），单价以台账为准；原始凭证列可写两个文件名 |
| 两者同键但数量不一致 | **不自动勾兑**；生成「冲突待审」两行或一行+冲突标记，人选留谁 |
| 台账有价、手写无价 | 允许自动补价，备注写 `单价来自台账:文件名` |

### 3. 写入大表的方式

- 产出 / 维护一份 `提货明细.xlsx`（或数据库表，结构与模板一致）。
- 每次任务只 **append 新指纹** + **update 未确认行**；已确认行除非人点「允许覆盖」否则不动。
- 另存 `ingest_log.jsonl`：每次识别的源文件、指纹、动作（新增/跳过/冲突），方便追溯。

## 五、日常怎么用（需求方侧）

建议目录（与方案书归档一致，略作细分）：

```text
财务归档/2026-08/提货/
  手写单/          ← 送货单照片
  供应商台账/      ← Excel 或台账截图
  _系统输出/
    提货明细.xlsx  ← 大表（可给人改）
    待复核.xlsx    ← 只含标黄/冲突行
```

操作：

1. 平时把新单丢进对应文件夹。  
2. 月底（或每周）点「汇总提货」。  
3. 先打开「待复核」：只核标黄和冲突。  
4. 确认后写回提货明细；下次回跑自动跳过已确认内容。

## 六、和其他大表的关系

| 来源变多时 | 进哪张表 | 说明 |
|------------|----------|------|
| 手写单、供应商台账、提货汇总 | **提货明细** | 一期主路径 |
| 速卖通/Temu 出库表、代发页 | **出库明细** | Excel 映射为主 |
| 退供 TEMU/速卖通 sheet | **退供明细** | Excel 映射为主 |
| 提现截图、提现流水 | **提现明细** | OCR 或 Excel |
| 转账/房租等 | **支出明细** | 与提货付款可关联单据号 |
| 计件、代发结算行 | **工资与代发** | 从代发 sheet 切结算块 |

同一套流水线，换「抽取模板 + 目标表」，不要为每种单据重写合并引擎。

## 七、落地节奏（建议）

| 阶段 | 做什么 | 结果 |
|------|--------|------|
| 现在 | 大表定型；spike 用真手写单测分码包数 | 知不知道抽得准 |
| 下一小步 | 升级 OCR schema（sizes/pack_size）；写台账 Excel 展开器 | 能产出标准中间 JSON |
| 再下一步 | 实现指纹去重 + 手写↔台账补价合并 + 待复核表 | 能稳定写入提货明细 |
| 之后 | 把出库/退供/提现 Excel 接入同一合并引擎 | 月底一键多表更新 |

**不要一上来就追求全自动入库。** 先做到「AI 填 80% + 人只核标黄」，比「全自动但数量翻倍」有用得多。

---

## 八、验收时盯的三个数

1. **手写单分码包数准确率**（比总金额更重要，因为金额常空）。  
2. **合并后是否数量翻倍**（抽 20 笔人工对原始单）。  
3. **待复核占比**（目标逐步降到 10%～20%）。

这三项过了，再加大自动写入比例。
